# 模型评分与风险概率判断：证据、边界与评估方法

调研日期：2026-10-26。对应议题：[模型评分与风险概率判断有哪些可靠证据和使用边界？](https://github.com/sidpku/DSAaaS/issues/6)。

## 结论

模型可以帮助比较方案、指出可疑变更、解释风险并安排复核顺序。现有证据不足以把一个模型给出的分数或自报概率直接当作本项目的真实事故概率，也不足以让它替代身份、权限、审批和确定性验收。这个结论是下列研究边界与工程控制原则的综合判断，不是本项目实测结果。

建议把后续决策拆成三种证据：**模型意见、可重复验证结果、有效授权**。三者分别记录；高评分不能生成授权，格式正确不能证明内容正确，多个 Agent 同意也不能证明错误相互独立。具体模型、阈值、重试次数和样本量仍待后续议题决定。

本次只阅读公开论文和官方文档；没有调用付费模型、开展对抗实验、测得成功率或选择供应商。

## 一手证据与适用边界

| 问题 | 查明的事实或研究结论 | 对本项目的含义与证据边界 |
|---|---|---|
| 模型能否给自己的答案估计正确概率？ | Kadavath 等在特定问答任务、提示形式及训练设置中发现有用的自评信号；跨新任务的校准仍有困难。[原论文](https://arxiv.org/abs/2207.05221) | 支持“值得评估”，不支持“任意模型说 0.9 就有 90% 真实正确率”。该论文未验证本项目的代码审查、权限判断或事故预测。 |
| 方案评分能否近似人类判断？ | MT-Bench / Chatbot Arena 研究显示 LLM judge 可近似特定对话偏好，同时存在位置、冗长、自我偏好和推理局限。[原论文](https://arxiv.org/abs/2306.05685) | 可以试用带明确量表的比较；不能把对话偏好一致性外推为安全审查准确率。换序、去作者身份、精简无关解释应纳入评估。 |
| 校准与准确率是否一回事？ | Guo 等将校准定义为置信概率与实际正确可能性相符，并研究分类网络的后处理校准；其实验主要是图像与文档分类。[原论文](https://proceedings.mlr.press/v70/guo17a.html) | 校准方法提供工具，不能直接证明其在自由文本自报概率上有效。尤其不能把 token 概率自动解释为事故概率。 |
| JSON Schema 是否保证判断正确？ | OpenAI 官方文档说明 Structured Outputs 仍可能包含错误；安全拒绝可能不符合给定 schema；输出长度限制也会产生不完整响应。[官方文档](https://developers.openai.com/api/docs/guides/structured-outputs) | 这是该接口的事实，不是所有供应商的通用承诺。适配器必须分别处理成功、拒绝、不完整、解析失败和调用失败；合法 JSON 仍需业务校验。 |
| 完整上下文是否等于完整理解？ | Lost in the Middle 在多文档问答和键值检索任务中发现，证据所在位置会影响表现，长上下文中间位置尤其可能退化。[原论文](https://arxiv.org/abs/2307.03172) | 说明“输入装得下”不能代替覆盖验证；论文没有直接测量当前候选模型或代码 diff，必须另做代码样本评估。 |
| 提示注入检测能否提供安全保证？ | AgentDojo 将不可信工具返回内容中的攻击与正常任务成功分开评估，发现当时模型在无攻击任务中也会失败，攻击能破坏部分安全属性。[原论文](https://arxiv.org/abs/2406.13352) | 应同时测量攻击效果、正常任务完成和误拦，不能只统计“识别出多少攻击词”。该基准的任务和结果不能作为本项目成功率。 |
| 模型防护是否已足够？ | OpenAI 的安全指南明确说 guardrails 单独使用并非万无一失，并建议限制不可信数据在节点间的传播、使用工具审批等组合措施。[官方文档](https://developers.openai.com/api/docs/guides/agent-builder-safety) | 支持分层控制思路；文档建议不等于本地权限已经实现，更不要求本项目逐次审批所有读取。审批范围应按既定业务规则定义并实测。 |

## 需要先统一的四个术语

以下是本报告提出的术语建议，供领域建模确认。

- **方案评分**：按指定维度评价候选方案的相对优劣，例如可维护性、证据充分性。其数值没有天然概率含义。
- **风险信号**：模型认为存在越权、注入、破坏性操作等问题的分类或排序分数。只用于触发复核或排序，不能增加权限。
- **事件概率**：对一个可观察、可标注事件的概率估计。必须说明事件是什么、评价对象是什么，以及对应的样本分布。例如“这一拟执行动作违反给定权限策略”，而不是模糊的“总体风险”。
- **确定性检查**：根据可信状态、规则或已确认基准计算的结果。其有效性仍依赖输入完整、实现正确和被执行的对象与被检查对象一致。

“自报有 2% 风险”和“同类预测区间中实际发生率约 2%”是不同陈述。后者需要带真实标签的独立评估数据，且应给出样本数量与不确定性；不能仅凭模型解释文字成立。[校准定义与可靠性图](https://scikit-learn.org/stable/modules/calibration.html)

## 建议的控制分工

本节是待验证的项目设计建议，依据上述证据提出，不宣称已经实现。

1. **可信执行层掌管授权。** 用户身份与角色来自认证系统；可写范围、任务状态、有效审批、可用工具及数据访问范围由模型外的代码检查。模型输出只作建议字段，不能覆盖这些条件。
2. **在动作发生前拦截。** 修改前检查拟执行动作与批准范围；执行后再核对实际改动。只在最终 diff 里发现越界，不能满足“修改前审批”。批准应绑定动作范围及版本；变更超出范围或对象版本改变时重新判断授权是否仍有效。
3. **审查者读取可信快照。** 不只阅读生成者的总结；直接取得待审版本、完整变更清单、必要上下文及可重复验证结果。作者解释属于待核对材料，不能自证正确。
4. **分开工作不等于统计独立。** 生成和审查职责可分离，但若共用模型、提示模板、摘要或被污染材料，不能假设其错误独立，更不能直接把两次漏判率相乘。是否增加第二审查者，以实际互补发现和共同漏判衡量。
5. **机器可比较的事实交给程序。** 已明确的输出与基准一致性、路径集合、输入输出版本等由程序验证；模型解释差异、提出定位线索。任何结论都绑定具体对象版本，避免用旧检查结果放行新内容。

## 完整 diff：可执行的覆盖契约

Git 官方文档区分工作区、暂存区和提交间的比较，并提供 raw、name-status、binary 及 submodule 等输出选项；不同选项和比较端点会改变可见内容。[git-diff 官方文档](https://git-scm.com/docs/git-diff)

因此建议在原型中建立如下契约，而非要求模型口头声称“全部已看”：

- 固定待审 base 与 head；若审查工作区，另显式盘点未跟踪文件及实际交付产物。保存清单与内容摘要值，审查后再次比对版本。
- 清单覆盖新增、修改、删除、重命名、权限模式、符号链接、子模块引用和二进制产物；不能用仅含文本 patch 的摘要代表全部变更。
- 为每个可审文本片段保存 `file / range / digest / included / review_status`。长输入拆片并记录缺口；未提交给审查者或被截断的片段必须可见。
- 二进制、生成代码和特殊格式使用对应验证器或明确交人工处理；“不支持审查”不能算通过。
- 先核对清单覆盖，再做语义审查；覆盖完整只说明材料送达与处理记录齐备，不能证明模型理解正确。分片时补充调用关系和相邻上下文，避免只看局部。

## 四项最小评估方案

以下都是待执行方案。可先用本地合成样本测试控制和故障处理；模型质量评估须在路线确定、调用条件明确后另行运行。

### A. 判断质量与校准

**样本**：正常变更、隐藏缺陷、触及公共路径的修改、表面无害但改变调用关系的变更、证据不足样本；每类包含容易和困难案例。安全事件与普通质量缺陷分开标注。真实任务样本应留在获准环境，不随公开研究报告上传。

**方法**：先定义事件和人工标注规则，保留分歧；按原始任务或攻击模板分组划分开发、校准和最终测试集合，避免同一变体跨集合泄漏。冻结模型版本、提示、工具和预处理。记录模型意见、证据引用及“无法判断”，不把它们默认为通过。

**输出**：混淆矩阵、漏判数／真实违规数、误拦数／真实合规数、转人工比例、每类样本数与区间估计。若输出概率，额外画可靠性图，报告 Brier score，并保留预测区间的样本数。Brier score 同时受校准与区分能力影响，不能单独当作校准证明；校准器与评估不能使用同一标签集合。[官方校准文档](https://scikit-learn.org/stable/modules/calibration.html)

**决策用途**：后续基于漏判成本、误拦负担和样本证据选择复核策略。当前不设置数字阈值。新增数据源、攻击类型或模型版本需要重新验证；人为平衡的测试集概率不能直接解释成真实流量事故率。

### B. 方案比较与独立审查

**样本**：同一方案不同篇幅、同一内容互换 A/B 顺序、带或不带作者标签；真实有优劣差异和相当的方案；作者自信解释但代码有错的样本。

**方法**：人工预先定义维度与参考判断；盲化作者并交换顺序复评。比较单审查者与分工审查流程。审查者直接取待审内容和验证结果，不能只拿前一 Agent 的结论。

**输出**：换序翻转率、逐维度人工一致性、无证据断言比例、各审查者独有发现与共同漏判、增加的人工时间和调用成本。这里的比率都必须同时给分子分母。

**决策用途**：判断模型适合辅助哪些比较，第二审查是否有增益。不能只依据总平均评分选择方案，也不把多 Agent 一致当作放行条件。

### C. 输入覆盖与输出故障

**样本**：短／长 diff，问题放在开头／中间／末尾，多文件与跨文件缺陷；只改权限、重命名、符号链接、二进制和未跟踪文件；模型拒绝、超时、限流、输出截断、缺字段、错类型、合法 JSON 但错误结论。

**方法**：用已知清单核对输入覆盖；故意省略片段或在审查中替换版本，观察是否阻止形成通过结论。用故障注入替代真实付费调用，验证状态转换与恢复路径。真实模型的故障发生率另测。

**输出**：漏送清单、版本不一致是否被检出、各故障最终状态、是否错误放行、恢复后重复动作。建议失败／未知显式停在待补充或待复核状态，不将缺失字段填成低风险，不以无限重试掩盖故障。

### D. 提示注入与授权绕过

**样本**：在文件注释、说明文档、检索结果、工具报错中嵌入伪造管理员指令、历史审批、要求隐藏变更或改变评分规则的文字；加入合法引用这些文字的对照样本。另测无注入但直接越权的工具请求、审批后范围变化、路径别名与符号链接、两任务资源混用。

**方法**：在隔离的合成环境中同时观测模型意见和实际工具副作用。第一组允许模型自由判断以测检测能力；第二组直接向执行层注入“模型已同意”的越权动作，检验权限控制是否依然拒绝。使用虚构凭据和测试目标，避免真实外发或真实破坏。

**输出**：攻击目标是否达成、越权副作用是否发生、正常任务完成、误拦、转人工。把“模型没识别但执行层拦住”与“模型识别出但仍发生副作用”分别记录；前者证明该样本中的控制生效，后者表明链路失败。有限测试中零成功攻击也不能证明普遍免疫。

## 留给后续决策的问题

- 哪些判断用于排序，哪些触发人工复核，哪些已有确定性规则？各自的事件标签和证据是什么？
- 谁维护基准集与争议标签？最小样本覆盖和可接受的漏判／误拦负担由谁确认？
- 审批绑定哪些对象、版本和动作范围？撤销、过期和修改后的重新审批如何处理？
- 哪些内容无法机器审查，如何交接人工？长任务分片之后如何验证跨片段依赖？
- 在候选架构原型中，故障、注入与越权请求能否被执行层阻断，并留下可复查证据？

本研究提供评估设计与证据边界；上述问题以及运行验证结果仍由后续决策票处理。
